# نظام السيطرة المخزنية والمحاسبية

نظام ويب متكامل لإدارة المخزون، المحاسبة، الخزينة، السلفة المستديمة، وعدة وحدات إدارية إضافية،
مبني بالكامل بـ JavaScript خام (بدون إطار عمل front-end) ومتصل بقاعدة بيانات **Supabase (PostgreSQL)**.

---

## ١. التقنيات المستخدمة

| الطبقة | التقنية |
|---|---|
| الواجهة | HTML + CSS خام + JavaScript (ES6+, بدون React/Vue) |
| قاعدة البيانات | Supabase (PostgreSQL) — مع Row Level Security (RLS) |
| المصادقة | Supabase Auth (بريد إلكتروني/كلمة مرور) |
| مكتبات خارجية (CDN) | `@supabase/supabase-js` (الاتصال بقاعدة البيانات)، `xlsx` (تصدير/استيراد إكسل)، `chart.js` (رسوم بيانية)، `jsbarcode` (توليد باركود) |
| النشر | أي استضافة ملفات ثابتة (Static Hosting) — لا يوجد Backend خاص، كل المنطق إما بالمتصفح أو بدوال/مشغّلات Postgres |

**لا يوجد خطوة بناء (build step)** — الملفات تُخدَّم كما هي مباشرة. يكفي رفع كل ملفات `.js`/`.html`/`.css` لأي استضافة ثابتة (Netlify, Vercel, GitHub Pages, أو حتى مجلد على أي خادم ويب عادي).

---

## ٢. الإعداد والتشغيل

### أ. قاعدة البيانات
1. أنشئ مشروع Supabase جديد (أو استخدم مشروعاً موجوداً).
2. شغّل ملفات الهجرة (migrations) **بالترتيب** من محرر SQL بلوحة Supabase. كل ملف مرحلة مستقل ويُشغَّل كاملاً مرة واحدة. (لو أضفت مراحل جديدة لاحقاً، تابع نفس الترتيب الزمني لأسماء الملفات).
3. تأكد من مراجعة كل سياسات RLS (`create policy ...`) بكل ملف هجرة — كُتبت بنمط عام متوافق مع الأدوار الموجودة (`admin`, `accountant`, `manager`, `auditor`)، لكنها **لم تُختبَر مقابل بيانات إنتاج حقيقية**. راجعها قبل أي استخدام تجاري.

### ب. الواجهة
1. عدّل `config.js` وضع فيه `SUPABASE_URL` و`SUPABASE_ANON_KEY` الخاصين بمشروعك.
2. ارفع كل الملفات (`index.html`, `styles.css`, وكل ملفات `.js`) لنفس المجلد على أي استضافة ثابتة.
3. افتح `index.html` — أول مستخدم يسجّل حساباً يحتاج تفعيلاً يدوياً من مدير نظام (أو من قاعدة البيانات مباشرة بتعديل `profiles.is_active = true` و`profiles.role = 'admin'` لأول حساب).

### ج. ترتيب تحميل ملفات JavaScript (مهم)
ملفات JS كلها `<script>` عادية (بدون `type="module"`) تشترك بنفس النطاق العام (Global Scope). **الترتيب مهم**: `config.js` و`supabaseClient.js` و`app.js` يجب أن تُحمَّل أولاً (تعرّف `DB`, `PAGE_RENDER`, `PAGES`, دوال مشتركة كـ `gv`/`sv`/`fmt`/`toast`)، وبقية الملفات (كل وحدة تسجّل صفحاتها بـ `PAGE_RENDER.xxx = ...`) تُحمَّل بعدها بأي ترتيب فيما بينها. الترتيب الحالي موثّق داخل `index.html` نفسه.

## ٣. الأدوار والصلاحيات

| الدور | الوصف |
|---|---|
| `admin` (مدير النظام) | صلاحية كاملة على كل شيء، بما فيها حذف نهائي، إدارة المستخدمين، تصميم الصلاحيات الأمنية |
| `accountant` (محاسب) | الوصول للمحاسبة والمخزون؛ يمكن تقييده بمخازن/فروع معيّنة من "المستخدمون والصلاحيات"؛ صلاحية الخزينة/الرواتب/السلفة المستديمة تحتاج تفعيلاً صريحاً (`can_treasury`) |
| `manager` (مدير) | صلاحيات إشرافية وتقارير، بدون إدخال يومي عادة |
| `auditor` (مدقق) | قراءة/مراجعة فقط بمعظم الشاشات |

يوجد أيضاً نظام **تجاوز صلاحيات مخصَّص** (صفحة "تصميم الصلاحيات الأمنية") يسمح لمدير النظام بمنح/سحب وصول أي دور لأي صفحة بالقائمة الجانبية دون تعديل الكود، مخزَّن بجدول `page_permissions`.

## ٦. قيود ومخاطر معروفة (اقرأها قبل أي استخدام تجاري)

1. **RLS غير مُختبَر مقابل بيانات إنتاج حقيقية.** كل سياسة أمان كُتبت بنمط عام متوافق مع الأدوار الموجودة — راجعها لكل جدول جديد بنفسك أو استعن بمراجعة أمنية مستقلة قبل تشغيله بأعمال حقيقية.
2. **فصل الفروع تطبيقي وليس صارماً بقاعدة البيانات.** يمنع المستخدم من رؤية/اختيار مخازن فرع آخر بالواجهة، لكن لا يمنع طلباً مباشراً لقاعدة البيانات من تجاوز هذا الفصل. يحتاج RLS مخصّص إضافي لعزل حقيقي.
3. **Single-tenant.** النظام مصمَّم لشركة واحدة بقاعدة بيانات واحدة. بيعه لعدة عملاء منفصلين يحتاج إما نسخة قاعدة بيانات مستقلة لكل عميل، أو إعادة تصميم لدعم Multi-tenancy.
4. **بعض أسماء أعمدة الجداول القديمة (قبل بداية هذا العمل) استُنتِجت من الاستخدام الفعلي بالكود وليس من توثيق رسمي**، لأن ملف `schema.sql` الأصلي كان فارغاً. أغلبها تم التحقق منها مباشرة، لكن ينصح بمراجعة شاملة.
5. **لا يوجد تخزين ملفات مدمج.** حقول مثل رابط ملف الأرشيف تعتمد على روابط خارجية (Google Drive وغيرها) وليس رفع ملفات فعلي داخل النظام.
6. **وحدات لم تُبنَ لعدم انطباقها على نظام ويب**: تصميم سطح المكتب، تطبيق مدير مخصَّص (native apps).
7. **تنفيذ أوامر SQL حر من المتصفح غير موجود عمداً** (ثغرة أمنية) — أي حاجة لتعديل قاعدة البيانات مباشرة تكون من SQL Editor بلوحة Supabase.

## ٧. الميزات المكتملة مقابل "قيد الإنشاء"

معظم الوحدات المذكورة بالقسم ٤ **شغّالة وظيفياً بالكامل** (إدخال، تعديل، حذف، تقارير، ترحيل محاسبي حيث ينطبق). عدد محدود من عناصر القائمة (تقارير متخصصة تحتاج مفاهيم غير موجودة كالأرقام التسلسلية أو تواريخ الصلاحية، ونقطة بيع POS كاملة، وبعض إعدادات البرنامج الغامضة النطاق) ما زالت تعرض صفحة "قيد الإنشاء" صريحة بدل محاكاة وظيفة غير موجودة.
